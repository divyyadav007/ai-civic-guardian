# Rules.md
## Project rules & guardrails for AI-assisted development of AI Civic Guardian
### (for use with Antigravity / agentic coding tools)

These rules should be kept accessible to the coding agent throughout the build (e.g., as a pinned context file) so generated code stays consistent across sessions.

---

## 1. Source of Truth

- `PRD.md` defines *what* to build and *why*. Do not add features not listed there without updating the PRD first.
- `ARCHITECTURE.md` defines *how* the system is structured — stack, service boundaries, data model, API surface. Any deviation (new dependency, new service, schema change) must be reflected back into `ARCHITECTURE.md` in the same change.
- `PHASES.md` defines *when* — do not build Phase 3 functionality while Phase 1 is incomplete. Finish and verify a phase's acceptance criteria before moving on.
- `DESIGN.md` defines the UX/screens — implement screens as specified; don't invent new navigation flows without updating it.

## 2. General Engineering Rules

1. **One module, one responsibility.** Follow the `backend/app/{api,services,models,schemas,ml,db,core}` structure in `ARCHITECTURE.md`. Route handlers stay thin; business logic lives in `services/`.
2. **All external providers behind an interface.** STT, geocoding, and (if swapped) classification providers must implement a common interface (`STTProvider`, `GeocodingProvider`) so providers can be swapped via config, not code changes.
3. **No secrets in code.** All API keys/config via environment variables (`.env`, loaded through `core/config.py`), never hardcoded, never committed.
4. **Every endpoint has a Pydantic schema** for request and response — no raw dict passthrough.
5. **Every DB schema change goes through an Alembic migration.** Never hand-edit the DB in a running environment.
6. **Async by default** for I/O-bound work (model inference calls, STT calls, geocoding calls) — use `async def` FastAPI routes and run classification/STT/geocoding concurrently where independent (see Architecture §5).
7. **Fail gracefully, never silently.** If classification confidence is below threshold, or STT/geocoding fails, return a partial draft with an explicit `needs_manual_input` flag — never fabricate a value.
8. **No client ever writes directly to storage or DB** — always via the backend API, so validation and auth are enforced centrally.
9. **All timestamps in UTC** in the DB; convert to local time only at the display layer.
10. **Tests required for:** routing engine logic, draft-generation templating, and any duplicate-detection logic — these are pure business logic and must be unit-testable without live ML calls (mock the ML services).

## 3. AI/ML-Specific Rules

1. **Model versioning:** every trained classification model artifact is tagged with a version string; the API response for a classification includes `model_version` so results are reproducible/auditable.
2. **Confidence thresholding is configurable**, not hardcoded — store threshold in config, not inline in code.
3. **Never let the ML layer auto-submit a complaint.** The citizen approval step (FR-5 in PRD) is a hard gate; there is no code path that submits a complaint without an explicit approval action from the user.
4. **Dataset provenance:** any training images used must be from a documented source (self-collected, public dataset with license, or synthetic/augmented) — log this in a `datasets/README.md`, not just in code comments.
5. **PII minimization in ML pipeline:** photos/voice notes sent to third-party STT/vision APIs should be stripped of unrelated EXIF metadata (e.g., precise device identifiers) before transmission where feasible.

## 4. API & Naming Conventions

- REST resource naming: plural nouns (`/complaints`, `/departments`, `/users`), nested only one level deep.
- Enum values in `snake_case` (e.g., `water_leakage`, `in_progress`).
- All API responses include `id`, `created_at`, `updated_at` where applicable.
- Error responses follow a single consistent shape: `{ "error": { "code": str, "message": str } }`.
- Frontend (mobile + dashboard) consumes the OpenAPI schema auto-generated by FastAPI — do not hand-maintain a separate API contract doc; regenerate client types from it.

## 5. Frontend Rules (Mobile + Dashboard)

1. Permissions (camera, mic, GPS) are requested with a clear rationale string shown to the user before the OS prompt — never request silently on app launch.
2. The Review & Approval screen (per PRD FR-5) must show every field that will be submitted — no hidden fields sent to the backend.
3. Loading and error states are required for every async screen (capture → classify → geocode → transcribe → draft) — never leave a spinner with no timeout/error path.
4. Department dashboard role-gates views: an officer for "Roads" must not see other departments' queues; only `admin` sees the cross-department view.
5. Follow `DESIGN.md` for screen inventory, navigation, and visual direction; do not introduce new screens without adding them there first.

## 6. Git & Review Rules

- Branch naming: `feature/<short-desc>`, `fix/<short-desc>`.
- Every PR references the `PHASES.md` phase/task it completes.
- No direct commits to `main`; PRs require at least a self-review checklist pass (lint, tests, and manual run-through of the acceptance criteria for that task).
- Keep commits scoped — one logical change per commit (e.g., don't mix a migration with an unrelated UI change).

## 7. When the Agent Is Unsure

If a requirement is ambiguous or missing from `PRD.md`/`ARCHITECTURE.md`:
1. Prefer the simplest option consistent with the stated architecture and stack.
2. Add a note under "Open Questions" in `PRD.md` rather than silently deciding and moving on for anything user-facing or data-model-affecting.
3. Never introduce a new third-party service/dependency not listed in `ARCHITECTURE.md` §2 without flagging it explicitly in the PR description.

## 8. Definition of Done (per feature/task)

A task is "done" only when:
- [ ] Code follows the module structure and naming rules above.
- [ ] Relevant unit tests pass (business logic) and are added if missing.
- [ ] API changes are reflected in the auto-generated OpenAPI schema and any client types are regenerated.
- [ ] DB changes have a corresponding Alembic migration, checked into version control.
- [ ] The corresponding checklist item in `PHASES.md` is marked complete.
- [ ] No secrets, debug logging of PII, or hardcoded config values are left in the diff.
